# 工具卡片与技能六部分

> **调用**：阶段 ⑤ 要把需求封成工具卡片、写 skill 六部分时用
> **触发**：工具卡片、function calling、入参出参、skill 六部分、认知资产、证据原文、工程硬规矩
> **路径**：`skills/superpowers/skills/项目启动准备/references/工具卡片与技能六部分.md`
> **边界**：只给填空模板与质量清单；不替用户写第 ③ 步的判断章法

## 一、工具卡片（一个工具一张）

标准 function calling；【】处按本项目补。

    工具名：【动词_名词，如 search_notes】
    作用：【一句话：这个工具干什么】
    入参：【参数名(类型、含义)】
    出参：【JSON 结构：[{字段名(类型、含义)}]】
    什么时候用：【什么场景 / 什么信号触发调它】
    什么时候不用：【边界：什么情况不该调它】

## 二、skill 六部分（真正值钱、AI 替不了的部分）

    ① 角色：你是【领域】资深【身份】，擅长【从什么资料判断什么】。
    ② 输入：【结构化资料清单：字段名 + 来源】
    ③ 分析步骤（逐步推理，不跳步 —— 你的认知资产）：
       1.【先看什么 → 怎么判断】
       2.【再看什么 → 怎么判断】
       3. ……
    ④ 输出格式（严格 JSON，字段不可少）：
       { "字段1": "…", "证据原文": ["…"] }   // 证据原文必须来自输入，不许编造
    ⑤ 护栏：结论必须有输入证据支撑；信息不足就写「资料不足，无法判断」，绝不臆测。
            【本场景的越权边界，如：只分析，不替用户发送 / 付款】
    ⑥ 例子：（贴一个你手动做过的真实范例：输入长这样 → 输出长这样）

①②④⑤⑥ 是壳，AI 能补；**第 ③ 步的章法 —— 先看什么、再看什么、在意什么 —— 是认知资产，只能从做过这行的人脑子里来。**

## 三、工程硬规矩

- 要求输出 JSON → 结果才能直接喂界面成表格。
- 要求「证据原文」＋「信息不足就说不知道」→ 防幻觉，把结论锚在证据上。
- 给一个例子 → 稳定性上一个台阶。

## 四、质量清单（交付后逐条过）

- [ ] 跑通实测：真实输入跑一遍，能直接运行出结果（不是「看起来对」）
- [ ] 职责单一：一个工具只干一件事；本次交付只含「先做的那一个」
- [ ] 结构符合：出参严格符合卡片写的 JSON 结构，字段不缺不错
- [ ] 证据可溯：结论能指到输入来源；信息不足如实说，不臆测
- [ ] 交付格式：结构化结果 / 固定字段，不是一段散文
- [ ] 合规生效：授权 / 平台 / 隐私 / 越权边界真的在跑（不是只写在需求里）
